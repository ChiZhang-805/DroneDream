# DroneDream 开发、发布与验收手册

更新日期：2026-10-22。

本文合并旧的代码交接、构建说明、测试清单、存储清理规则和阶段性验收结论。具体命令会随仓库变化；执行前以仓库 README、脚本参数和当前 Git 状态为准。

## 1. 开始工作

每次修改前：

1. 阅读工作区 `AGENTS.md`、`DroneDream/docs/guides/PROJECT_MEMORY.md` 和产品原则文档。
2. 分别检查要操作的 Git 仓库或 worktree：`git status --short --branch`、`git diff --stat`，必要时检查子模块。
3. 不 reset、不 clean、不覆盖脏工作树，不把旧交接中的分支、版本或路径当作当前事实。
4. 明确本轮目标属于前端、桌面宿主、后端、Agent Core、Runtime、资产、构建或安装中的哪一层。
5. 对真实缺陷先复现并保存最小证据；不要用增加超时、跳过 gate 或重复重试掩盖根因。

长时间构建失败后，除修复当前错误，还应沿剩余构建、打包、安装与签名链路提前核对路径、生成资源和输入依赖，一并修复能确定的问题。已有快速检查应放在耗时编译之前；不要每次只改一处错误就重新完整编译，也不要为此新增审计文件或产品运行限制。

正常路径应直接、可读、能运行。输入在负责它的边界校验一次，内部依赖清楚的契约继续执行。只对实际发生的故障、状态变化和真正的飞行安全条件增加处理，避免防御性代码拖慢任务或制造新的卡死点。

## 2. 修改原则

- 用户输入按模糊自然语言设计，不能把地图、机型、航点和算法参数转嫁给用户。
- 页面删掉说明性文字时，只移除展示；底层权限、安全和完整性校验仍保留在其职责层。
- 地图、飞行器和模型包使用版本化身份。升级内置资产必须依据发布清单中的明确替换关系迁移；不能任意替换用户上传资产的固定版本。
- 规划、执行、完成和证据使用同一次运行身份。不能把不同运行的截图、轨迹和最终状态拼成一次成功。
- 普通路径偏差可在线修正；碰撞、穿透、损毁、受控实体身份错误和不可恢复失控必须失败。
- 任务结束后的正常传感器停流不能反过来否定已冻结的完成证据；飞行中的断流仍必须由安全层处理。

## 3. 验证层次

按风险和成本逐级验证：

1. **静态与聚焦测试**：格式、类型、契约、关键单元测试和受影响模块回归。
2. **构建验证**：前端、后端、桌面宿主和 Agent Core 的实际构建，不以编辑器无报错代替。
3. **资产验证**：地图/机型可解析、依赖完整、坐标一致、碰撞几何有效、真实预览生成。
4. **规划验证**：路径不穿建筑、净空足够、转弯可跟踪、起点/终点/交接点关系正确。
5. **物理仿真**：真实 PX4 SITL 与 Gazebo，使用实际模型、地图、遥测、视觉/深度来源和受控实体。
6. **安装版流程**：从桌面快捷方式启动，真实登录，输入自然语言，确认计划，执行、返航、降落，关闭重开后核对状态。
7. **五版本复验**：Universal、SIM、LAB、FIELD、AGENT 全部更新，验证图标、快捷方式、登录落点、Runtime 共用与进程隔离。

界面检查、单元测试、构建成功和动画播放都不能证明任务完成。真实任务成功至少需要核对路径、遥测、碰撞、载荷动作、模型参与、执行器退出、受控落地、数据库状态和同一次运行的最终收据。

## 4. 自然语言人工验收

安装版主验收使用英文，贴近默认语言。推荐从下列用户表达开始：

```text
Please pick up a set of lab instruments from the chemistry building and bring it back.
```

也应覆盖更模糊或依赖上下文的表达，例如：

```text
Please get something for me.
Bring back the documents from the physics building.
Pick up the sample from the chemistry department and return here.
Go to the building where the computer science labs are and collect the package.
```

预期流程：

1. 双击当前版本桌面图标，确认启动步骤完整、无截断，并进入登录页。
2. 使用专用普通测试账户在软件内登录。密码只存在本机 DPAPI 加密凭据中，不进入源码、文档、聊天或普通日志。
3. 登录后进入当前版本自己的 Chatbot。
4. 输入自然语言。信息真正不足时，Agent 只追问缺少的地点、物品或接收人；已有地图线索时先形成候选。
5. 检查计划使用正确地图、正确机型、正确建筑及其合格交接点，包含取件、载荷确认、返回和安全降落。
6. 点击开始后，检查聊天内运行电视、二维实际路线和可用相机视角；二维路线不得显示穿楼直线。
7. 允许无人机对普通跟踪偏差持续修正；出现真实失败时结束本轮，记录原因，修复并更新安装版，然后从桌面启动重新验收。
8. 成功后确认 PX4 `ON_GROUND`、无碰撞/中止、载荷动作和阶段判断完整。关闭软件并重新打开、登录，确认完成记录仍存在。

无地点的“Please get something for me”应触发自然澄清，不能被硬编码到通用交付点。物品或部门能够指向建筑时，应使用地图语义推断候选，但不能声称该物品真实库存已经得到证明。

起飞地点规则另行验收（2026-10-22）：

- 默认点：`Please pick up some lab instruments from the chemistry building.` 不追问起点，重复新任务仍绑定当前地图同一固定默认点；“from the chemistry building”在此修饰取件，不得误作起飞。
- 明确起点：`Start at the physics building, pick up the sample from the chemistry building, and bring it back.` 起点和默认返程点都应对应物理楼的可用起飞位置，取件目标为化学楼。
- 别名：将明确起点分别改为 `Physicum`、`the physics building`、`物理楼`，应解析到同一地点；中文例句为“从物理楼出发，去化学楼取样品再回来”。
- 未知或歧义：明确指定不存在的建筑，或地图中对应多个地点的别名，应自然澄清，不能静默退回默认点。
- 执行一致性：逐案核对计划起点、运行坐标绑定、仿真出生位置、首次有效遥测和返程落点。单元测试、提示词修改与名称解析成功不能替代非默认起点的安装版物理验收。飞行中改令不能重新初始化到固定默认点。

## 6. 失败—修复—复验循环

1. 保存失败运行的输入、版本、运行身份、日志、路径、遥测、碰撞和终态。
2. 区分自然语言理解、地点绑定、路径规划、资产契约、Runtime、飞控、前端状态和完成判定中的真实根因。
3. 修复问题时检查同类地点、同类资产和其他版本，避免只给报错案例打补丁。例如一个建筑缺交接点时，应复核整张地图的建筑—入口—交接点关系。
4. 运行聚焦测试和必要回归，构建新版本。
5. 更新所有受影响的已安装桌面版本；确认更新一版不会关闭其他版或共享 Runtime。
6. 从桌面快捷方式重新开始全流程，不沿用失败运行手工改成成功。

失败证据保留到根因和最终成功能够复核。没有最终总结、必要检查或可信终态的运行不能验收。

## 7. 发布与安装

GitHub Actions 的名称按职责保持简短：`检查产品代码` 验证应用代码，`检查运行环境` 验证 Runtime 配置与打包约定，`构建安装包` 从源码生成桌面安装器，`签名更新包` 为五版交付包生成更新签名，`发布运行环境` 构建并发布 WSL 镜像，`发布官网` 部署网站，`清理旧记录` 执行保留规则。运行记录不是源码分支；旧分支的失败应先在当前源码复现和修复，不盲目重跑历史提交。

`发布运行环境` 需要带 `dronedream-runtime-builder` 标签的专用 Linux x64 runner；触发之前确认该机器在线。没有注册机器时应恢复构建机器，不能以跳过镜像构建或仿真验证的方式制造成功记录。上传失败先检查现有发布资产是否完整，再决定恢复上传或重新构建，不覆盖已经公开的不可变版本。

- 源码事实以审查后的提交为准；本地构建目录不是发布事实源。
- 发布暂存位于 `Build/Release-Staging`，只保留当前源提交和版本的完整五版本集合。
- 正式发布以 GitHub Release 资产、摘要、签名和发布清单为准。
- 本机缺少自动更新签名私钥时，先检查 GitHub Actions 的 `TAURI_SIGNING_PRIVATE_KEY` Secret 和现有 `签名更新包` 工作流。可将同一源提交的五版安装包、摘要和收据上传到草稿 Release，在云端签名后取回签名及收据，验证后再同步发布；不要求用户导出或在聊天中提供私钥。自动更新签名与 SignPath 的 Windows 发布者签名是两件事，不能混为一谈。
- PR 或发布说明应写清具体触发条件、修改后的行为和验证证据，不保留无关的尝试过程。
- 桌面更新后核对五个图标和快捷方式。应用图标缺失、登录后进入错误产品页或安装器误关兄弟版本均视为交付失败。
- 只生成安装器而未安装复验，不能称为软件已经更新。

## 9. 清理规则

- GitHub Actions 按现用工作流分别保留最近一次成功、尚未被新成功解决的最近一次失败、当前正式与必要回退版本关联记录，以及 SignPath 正式证书复核所需的固定记录。正在运行或排队的任务保留，其余已被替代及废弃工作流记录自动清理。规则见 `release/distribution/desktop/RELEASE_POLICY.md`；不删除 Release、Tag、更新渠道或 Git 源码历史。

### 可重新生成

- 各工作树 `desktop/src-tauri/target` 等 Rust/Cargo 构建缓存。
- `codex-cache`、构建 `temp`、npx 下载缓存和已结束的 Runtime 临时探针目录。
- 已被新版本替代且有完整收据的 staging/build 副本。

清理前确认相关进程已停止、路径被 Git 忽略或有可重建来源，并记录文件清单及大小。

### 限期保留

- Candidate/Staging：每个源提交和版本保留最近一次完整五版本集合，通常不超过 14 天。
- Visual QA：保留最终截图、receipt 和失败根因，通常不超过 30 天。
- 浏览器下载：保留当前待测安装器及摘要；相同重复下载和已替代安装器在测试结束后移出。
- Runtime 数据库备份：只保留产品能够识别的最近 5 份普通 `.db` 备份。

### 必须保留或走正式流程

- 脏 Git 工作树、未推送提交、唯一恢复材料、迁移收据、当前安装目录、凭据、Runtime 所有权标记和 VHDX。
- 用户实验数据及其数据库关联。
- 无法证明来源、哈希或可恢复性的唯一安装器和唯一测试证据。

用户当前要求：需要删除的文件统一移动到 `Pending-User-Deletion`，由用户最终删除。项目代理不直接永久删除保留或未分类材料。

## 10. 历史资料的处理

旧 `Documents/Code-Handoff` 中的大量 `source-inventory-*.json` 是不同时点生成的完整源码清单，单份约 24–30 MiB，彼此高度重叠；它们不是当前源码，也不应继续作为日常文档。旧课程代码、PPT 生成脚本、图片素材、阶段交接和过时运行命令同样不进入精简后的文档主目录。

历史材料移动前后在内存和对话中核对路径、文件数、总字节及必要摘要；不新增审计、扫描或整理报告。需要追溯旧阶段时优先查 Git 历史和已有的运行收据，不恢复整批重复源码清单。
