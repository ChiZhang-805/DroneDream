# DroneDream 更新、维护与零停机发布通俗指南

> 文档用途：帮助非技术人员理解网站为什么有时会关闭部分入口、现代网站和游戏如何边运行边更新，以及 DroneDream 将来可以怎样实现网站、后端、桌面软件和 Runtime 的平滑升级。
>
> 状态说明：本文包含截至 **2026-07-30** 的 DroneDream 状态快照。证书、线上版本和发布状态可能随时间变化；实际操作前应重新核验线上入口和最新发布回执。

## 1. 先说结论

现代系统通常不需要为了每次更新而让所有用户退出。

更常见的做法是：

1. 旧版本继续为现有用户服务。
2. 新版本在另一套目录或服务器中完成上传、构建和测试。
3. 新版本通过健康检查后，再把新用户流量切换过去。
4. 已经开始的游戏对局、仿真任务或长时间作业继续使用原来的版本，直到任务自然结束。
5. 如果新版本出现问题，可以迅速切回旧版本。

只有高风险数据库迁移、安全事故、数据修复或新旧协议完全不兼容时，才可能真正进入“维护中，暂时无法使用”的状态。

## 2. DroneDream 截图里的入口为什么变灰

截图中的地址是：

```text
http://47.93.180.216/
```

浏览器把它标记为“不安全”，因为这个入口使用的是没有 TLS 加密的 HTTP。

DroneDream 在这种入口上会保留：

- 官网浏览；
- 产品和工作流介绍；
- 在线说明书；
- 社区只读内容；
- 安装包下载。

但会主动禁用：

- 登录；
- 网页控制台；
- 社区发帖和评论；
- 支付；
- 托管模型授权；
- 其他需要发送账户或敏感数据的操作。

这叫作 **安全锁定（security gate）**，不是普通的维护停机。

### 2.1 为什么 HTTP 入口不能开放登录

如果在没有 HTTPS 的页面中提交密码、Cookie、支付信息或访问授权，中间网络设备理论上可能：

- 读取数据；
- 修改页面；
- 替换下载内容；
- 伪造提交请求；
- 诱导用户把敏感信息发送到错误的服务器。

因此，安全的处理方式不是“先让它能用，以后再修”，而是让敏感入口在可信 HTTPS 尚未成立时明确地保持不可用。

### 2.2 安全锁定与维护停机的区别

| 状态 | 用户能看到什么 | 主要原因 |
|---|---|---|
| 安全锁定 | 公共内容可访问，敏感功能禁用 | 当前入口缺少可信 HTTPS 或其他安全前置条件 |
| 部分维护 | 大部分功能可用，某个模块暂时不可用 | 单个服务升级、数据修复或功能迁移 |
| 全站维护 | 只能看到维护提示页 | 高风险或不兼容变更，必须阻止所有写入 |
| 正常零停机发布 | 用户通常没有明显感觉 | 新旧版本并行，验证后原子切换 |

## 3. 网站更新时一定要关站吗

不一定。现代网站通常使用以下方式保持服务。

### 3.1 原子目录切换

适合静态网站和前端资源。

```text
用户继续访问旧目录
        ↓
新网站上传到新版本目录
        ↓
完整校验新目录
        ↓
current 一瞬间切到新目录
        ↓
旧目录保留，随时可以回滚
```

切换通常只需要不到一秒。用户已经打开的页面会继续运行已经加载到浏览器内存中的旧版 JavaScript；刷新页面或重新打开时，才会加载新版。

DroneDream 的阿里云静态站已经使用类似的版本目录和 `current` 原子切换方式。

### 3.2 蓝绿部署

同时保留两套完整环境：

- 蓝色环境：当前线上版本；
- 绿色环境：准备上线的新版本。

绿色环境完成测试后，负载均衡器把流量从蓝色切到绿色。出现问题时可以快速切回蓝色。

适合：

- 网站；
- API；
- 后端服务；
- 需要快速回滚的发布。

### 3.3 滚动更新

当系统有多台服务器时，一次只更新其中一部分：

1. 其余服务器继续接待用户。
2. 更新一台或一组服务器。
3. 健康检查通过后再更新下一组。
4. 直到全部完成。

用户通常不会感受到停机。

### 3.4 灰度或金丝雀发布

新版先只开放给少量用户，例如：

- 内部测试人员；
- 1% 的真实用户；
- 某个地区；
- 某个账户组。

观察错误率、性能和用户反馈后，再逐步扩大到 5%、20%、50% 和 100%。

### 3.5 功能开关

代码可以提前部署，但功能保持隐藏。

准备完成后只需打开配置开关，不必重新部署全部代码。出现异常时也可以立即关闭新功能。

典型用途：

- 新社区；
- 新支付方式；
- 新模型供应商；
- 实验性优化器；
- 新版控制台页面。

### 3.6 向后兼容的数据迁移

数据库变化通常采用“扩展—迁移—收缩”流程：

1. 先增加新字段，但保留旧字段。
2. 让新旧程序都能正常工作。
3. 后台逐步迁移历史数据。
4. 所有程序都切到新字段。
5. 最后才删除旧字段。

如果一开始就直接删除旧字段，仍在运行的旧程序可能立即报错，这时就容易被迫停机维护。

## 4. 王者荣耀一边运行一边更新的原理

一局游戏通常会固定使用某个游戏服务器版本。

```text
玩家开始一局游戏
        ↓
这一局锁定在旧版本
        ↓
后台完成新版发布
        ↓
旧对局继续，不被中途替换
        ↓
玩家结束这一局
        ↓
下一局使用新版
```

这样可以避免：

- 游戏规则中途改变；
- 角色状态丢失；
- 客户端与服务器协议突然不一致；
- 对局被强制中断；
- 新旧技能或数值混在同一场比赛中。

### 4.1 为什么背包和社区可以单独更新

大型游戏通常会把系统拆开：

- 游戏对局服务；
- 背包和资产服务；
- 好友服务；
- 社区服务；
- 活动页面；
- 商城服务；
- 登录服务；
- 图片和资源 CDN。

因此，更新社区不需要重启游戏对局服务器；更新背包也不必打断正在进行的比赛。

### 4.2 什么可以实时更新

通常可以实时变化的内容包括：

- 服务器返回的数据；
- 活动配置；
- 商品列表；
- 公告；
- 图片和资源；
- 远程网页；
- 部分脚本或资源包。

通常不适合在运行中直接替换的内容包括：

- 正在运行的可执行文件；
- 游戏引擎核心；
- 驱动和反作弊模块；
- 不兼容的通信协议；
- 需要重建本地数据库的重大版本。

## 5. 为什么有些更新自动完成，有些需要用户确认

这不只由版本号决定，还取决于风险、体积、兼容性和用户当前状态。

| 更新类型 | 推荐体验 |
|---|---|
| 纯服务器算法修复 | 用户无感，不需要更新客户端 |
| 文案、模型列表、远程配置 | 打开页面时自动获得 |
| 小型桌面补丁 | 后台下载，退出软件时安装 |
| 普通功能版本 | 下载后提示“重新启动并更新” |
| 大型 Runtime 更新 | 显示体积和预计时间，让用户确认 |
| 严重安全漏洞 | 可以要求强制更新 |
| 协议完全不兼容 | 必须升级后才能继续连接 |

一种常见策略是：

- 补丁版本：允许后台自动下载；
- 普通功能版本：下载后由用户确认安装；
- 大版本：展示更新说明、备份和兼容性提示；
- 安全更新：设置最后升级期限或强制升级。

版本号只是参考。即使版本号变化很小，只要涉及数据迁移或安全边界，也可能需要用户确认。

## 6. DroneDream 可以怎样实现平滑更新

DroneDream 可以把更新分成四层。

### 6.1 第一层：网站与远程内容

适用于：

- 官网页面；
- 在线说明书；
- 社区只读内容；
- 模型列表；
- 普通文案；
- 远程配置。

推荐方式：

- 一次构建同一份静态制品；
- GitHub Pages 与阿里云部署相同字节；
- 新目录完成校验后再原子切换；
- 资源文件使用内容哈希命名；
- 保留旧目录用于回滚。

用户体验：

- 已打开页面继续运行；
- 刷新页面或重新打开后加载新版；
- 通常不需要维护停机。

### 6.2 第二层：后端与控制台服务

适用于：

- 登录；
- 社区写入；
- 模型调用；
- 任务管理；
- 支付；
- API。

推荐方式：

- 蓝绿或滚动部署；
- 新旧 API 在迁移期保持兼容；
- 使用功能开关逐步开放；
- 每次发布先健康检查；
- 观察错误率、延迟和任务失败率；
- 出错时自动或人工回滚。

### 6.3 第三层：正在运行的仿真 Job

仿真任务与游戏对局类似。

建议给每个 Job 固定：

- 桌面客户端版本；
- API 协议版本；
- 后端版本；
- Runtime 版本；
- PX4/Gazebo 环境版本；
- 参数目录和证据格式版本。

已经开始的 Job 继续使用原版本，直到完成或安全停止。新建 Job 再使用新版。

这样可以避免同一次实验中途切换算法、Runtime 或数据格式，保证结果可复现。

### 6.4 第四层：Windows 桌面软件和 Runtime

推荐流程：

1. 软件启动后检查更新元数据。
2. 在后台下载新安装包或差分包。
3. 校验版本、文件大小、SHA 和 updater 签名。
4. 下载到独立临时目录，不覆盖正在运行的程序。
5. 如果用户正在运行 Job，等待任务结束。
6. 显示“更新已准备完成”。
7. 用户点击“重新启动并更新”，或者退出软件时自动安装。
8. 安装失败时保留旧版本和用户数据。

这不需要用户先卸载旧版，再从官网重新安装。

Runtime 体积较大，可以采用：

- 分片下载；
- 断点续传；
- 下载后重组；
- 整体 SHA 校验；
- 签名校验；
- 新旧 Runtime 并存；
- 新 Job 使用新版，旧 Job 保留原版本；
- 确认稳定后再清理旧 Runtime。

## 7. 推荐的 DroneDream 更新策略

### 7.1 自动更新

可以自动处理：

- 官网静态内容；
- 后端兼容性修复；
- 模型列表和普通配置；
- 已验证的小型桌面补丁；
- 不影响现有 Job 的资源更新。

### 7.2 需要用户确认

建议用户确认：

- 桌面程序需要重启；
- 下载文件较大；
- Runtime 需要较长安装时间；
- 数据格式需要迁移；
- 可能影响现有插件或本地环境；
- 需要管理员权限。

### 7.3 强制更新

只建议用于：

- 严重安全漏洞；
- 旧协议已经停止服务；
- 旧版可能损坏数据；
- 法律、隐私或支付要求发生变化；
- 服务器无法再安全兼容旧版。

## 8. 关于版本号和内部构建号

内测阶段，DroneDream 曾按产品要求持续显示 `1.0.0`，并用新安装包替换旧的 1.0.0。

这种方式适合短期内测，但不适合长期自动更新，因为更新器需要明确判断：

- 哪一个版本更新；
- 当前用户安装的是哪一次构建；
- 是否已经下载过；
- 是否可以回滚；
- 缓存中的同名文件是不是旧文件。

一种折中方案是：

```text
对外显示版本：DroneDream 1.0.0 Preview
内部构建编号：2026.07.30.2
更新通道：preview
```

正式发布后，更推荐每份不同字节使用不可重复的版本或构建标识，例如：

```text
1.0.0-beta.2
1.0.0-beta.3
1.0.0
1.0.1
1.1.0
```

这样才能可靠完成版本比较、缓存控制、回滚和审计。

## 9. 一次理想的桌面更新过程

```text
软件启动
  ↓
检查 preview 或 stable 更新通道
  ↓
发现新版本
  ↓
后台下载到 staging 目录
  ↓
验证 SHA、大小、签名和版本
  ↓
用户正在运行 Job？
  ├─ 是：等待 Job 结束
  └─ 否：提示更新已准备完成
  ↓
用户点击“重新启动并更新”
  ↓
关闭旧进程
  ↓
原子替换程序文件
  ↓
启动新版并执行健康检查
  ↓
失败则回滚旧版
```

可以给用户提供选项：

- 自动下载所有更新；
- 只自动下载安全补丁；
- 下载完成后提醒；
- 仅手动检查；
- 在退出软件时安装；
- 暂缓到当前 Job 完成。

## 10. 一般需要多长时间

以下只是常见范围，实际时间取决于网络、文件大小和迁移复杂度。

| 类型 | 后台准备时间 | 用户不可用时间 |
|---|---:|---:|
| 静态网站原子更新 | 1～10 分钟 | 通常为 0，切换小于 1 秒 |
| 普通后端滚动更新 | 5～30 分钟 | 通常为 0 |
| 小型桌面更新 | 1～10 分钟下载 | 最终替换约 10～60 秒 |
| 大型 Runtime 更新 | 十几分钟到数小时 | 可后台下载，最终切换通常很短 |
| 兼容数据库迁移 | 数秒到数小时 | 通常为 0 |
| 不兼容数据库迁移 | 数分钟到数小时 | 可能需要维护窗口 |
| 安全事故处理 | 无固定时间 | 可能立即关闭敏感入口 |

## 11. 什么时候应该真正进入维护模式

满足以下情况之一时，可以考虑关闭部分或全部入口：

- 正在修复可能导致用户数据损坏的问题；
- 数据库必须执行无法兼容新旧程序的迁移；
- 登录、支付或权限系统出现安全漏洞；
- 无法保证旧客户端与新服务器的协议兼容；
- 当前只有单台服务器，重启期间没有替代实例；
- 需要恢复备份或修复不一致数据；
- 新版本没有可靠回滚路径。

维护页面应该告诉用户：

- 哪些功能受影响；
- 已经开始还是计划维护；
- 预计恢复时间；
- 数据是否安全；
- 公共浏览或下载是否仍然可用；
- 状态页面或后续通知地址。

## 12. DroneDream 当前基础与尚未完成的部分

截至 2026-07-30，DroneDream 已经具备一些基础：

- GitHub Pages 与阿里云可以消费同一份静态网站制品；
- 阿里云站点支持版本目录和回滚目录；
- Windows 安装包有 SHA 校验文件；
- Tauri updater 元数据和 updater 签名已经存在；
- Runtime 有独立清单、签名、分片和重组验证；
- 网站和控制台具备 HTTP 入口 fail-closed 保护。

仍需完成或正式决策的部分包括：

- 为 `getdronedream.com` 获得包含正确域名的可信 TLS 证书；
- HTTPS 正常通过后重新开放并验证网页登录、社区写入和安全控制台；
- 决定 stable 与 preview 更新通道；
- 使用不可混淆的内部构建号或递增版本；
- 修复 prerelease 无法通过 GitHub `releases/latest` 自动发现的问题；
- 完成桌面后台下载、暂停、断点续传、重启安装和回滚体验；
- 规定 Job 与 Runtime 的版本锁定策略；
- 建立灰度发布、功能开关、错误监控和自动回滚门槛。

## 13. 推荐实施顺序

### 阶段 A：先建立可信入口

1. 修复 `getdronedream.com` TLS 证书。
2. 正常主机名和信任链验证通过。
3. 再启用 HTTPS 强制。
4. 重新测试登录、社区写入、控制台和支付边界。

### 阶段 B：建立更新通道

1. 定义 `preview` 和 `stable`。
2. 每次不同安装包使用唯一构建标识。
3. 更新元数据固定包含版本、大小、SHA、URL、发布日期和最低兼容版本。
4. 客户端只信任经过签名和校验的元数据。

### 阶段 C：实现桌面后台更新

1. 后台检查和下载。
2. 支持断点续传。
3. 不打断正在运行的 Job。
4. 退出或用户确认后安装。
5. 安装失败自动回滚。

### 阶段 D：实现后端零停机更新

1. 蓝绿或滚动部署。
2. API 向后兼容。
3. 数据库扩展—迁移—收缩。
4. 现有 Job 锁定旧版本。
5. 新 Job 使用新版。

### 阶段 E：逐步发布与监控

1. 内部账户验证。
2. 1% 灰度。
3. 观察错误率、延迟和 Job 成功率。
4. 分阶段扩大流量。
5. 达到异常门槛时自动停止或回滚。

## 14. 发布前检查清单

### 网站

- [ ] 新旧入口使用同一源码提交。
- [ ] GitHub Pages 与阿里云使用同一制品，不分别构建。
- [ ] `build-manifest.json` 一致。
- [ ] `SHA256SUMS` 一致。
- [ ] HTML、JavaScript、CSS 和下载元数据一致。
- [ ] 桌面和移动端均完成截图检查。
- [ ] 英文和简体中文均完成验证。
- [ ] 多浏览器矩阵通过。
- [ ] 旧目录和回滚入口仍然可用。

### 后端
